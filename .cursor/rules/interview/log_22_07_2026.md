# Mock Interview Log — 22/07/2026

## 1. Nội dung Phỏng vấn

**Câu 1 (Warm-up): Giới thiệu bản thân và lý do nghỉ Firegroup**
- **Trả lời:** Lập trình viên 4 năm kinh nghiệm, 3+ năm tại Firegroup. Nêu bật 2 dự án OneMobile, OneLoyalty. Tech stack: RN, TS, TanStack Query, Zustand/Redux. Thành tựu lớn nhất: Tối ưu bundle từ 45MB xuống 28MB.
- **Follow-up (Lý do nghỉ):** Giải thích là do công ty layoff/cắt giảm dự án, quyết định vĩ mô không phải do năng lực, vẫn code và làm task đầy đủ cho đến khi app vào chế độ maintenance.

**Câu 2 (State Management): Phân bổ lưu trữ Danh sách sản phẩm và Giỏ hàng**
- **Trả lời:** Dùng TanStack Query cho List sản phẩm (Server state, có sẵn loading/error/skeleton). Dùng Redux cho Giỏ hàng (Client state UI). Tránh dùng Redux cho API để bớt boilerplate.
- **Follow-up (Optimistic Update khi thêm giỏ hàng):** Giải thích ranh giới (boundary) cực tốt: Không dùng Optimistic update cho các thao tác nhạy cảm như giỏ hàng/thanh toán để tránh race condition hiển thị sai tiền. Chỉ dùng cho UI đơn giản như nút Like, thả tim.

**Câu 3 (Auth & API): Xử lý 401 và luồng Refresh Token (có nhiều request cùng lúc)**
- **Trả lời:** Đặt logic trong Axios Interceptor. Khi API bị 401, check xem token còn hạn hay không. Dùng một biến callback (hoặc queue) để tạm dừng các request phía sau (bind lại) trong lúc đang gọi API refresh token. Nếu refresh thành công, dùng token mới chạy tiếp. Nếu thất bại, đẩy về login. Kỹ thuật này gọi là Singleton Refresh Token.
- **Follow-up (Lưu trữ token an toàn):** Không dùng AsyncStorage vì không mã hóa. Với Expo dùng SecureStore, với RN CLI dùng thư viện React Native Keychain. Dữ liệu lưu vào Keychain (iOS) và KeyStore (Android) được mã hóa.

**Câu 4 (Performance): Giảm bundle size 45MB -> 28MB**
- **Trả lời:** Nêu 4 action: (1) Nén ảnh xuống 80% chất lượng và resize đúng khung hình. (2) Gỡ các dependency rác không còn sử dụng. (3) Tree shaking (ví dụ import đúng hàm Lodash cần dùng). (4) Quét toàn project xóa file không dùng.
- **Follow-up (Công cụ đo đạc Bundle):** Ứng viên nhầm lẫn trả lời là dùng React Profiler đo trên bản Release. (Lưu ý: Profiler dùng đo FPS/Render chứ không đo file size JS).

**Câu 5 (Tình huống thực chiến): Debug Crash Android production**
- **Trả lời:** Cách xử lý tức thời là dùng Feature Flag (hoặc nhờ BE trả cờ API) để tắt tính năng đó đi, "cầm máu" cho user dùng được app trước.
- **Follow-up (Tìm dòng code lỗi):** Dùng Firebase Crashlytics để xem log. (Lưu ý: Thiếu keyword "Source Map" để đọc file JS minified).

**Câu 6 (AI Workflow): Quản lý rủi ro "vibe coding"**
- **Trả lời:** Setup các Rule/Skill chuẩn trong Cursor. Dùng kỹ thuật `/grill-me` bắt AI hỏi ngược 3-5 câu edge case. Dùng TDD bắt chạy test fail rồi mới code pass. Dùng `/shape-audit` check file > 250 dòng và vi phạm Single Responsibility. Không bao giờ "Accept All".

### Câu hỏi thực tế từ Ocany: "Khi user tăng lên 10.000 người, về mặt kiến trúc system bên trong app bạn sẽ làm gì?"
- **Câu trả lời của ứng viên lúc đó:** "Xử lý tải server là việc của Backend và DevOps. Về phía Mobile, tôi chỉ tập trung tối ưu bundle size nhỏ nhất có thể để trải nghiệm user tốt nhất."
- **Nhận xét & Phân tích:** Câu trả lời này **KHÔNG SAI nhưng CHƯA ĐỦ SÂU (Defensive)**. Nó thể hiện mindset "đẩy việc cho BE" và hơi né tránh phần Architecture của Mobile. Khi app tăng scale lên 10.000+ users, team phình to ra, kiến trúc app bên trong (Mobile Architecture) cũng sẽ chịu áp lực (conflict code, phình size, maintain khó).
- **Cách trả lời chuẩn (Strong Middle):**
> "Đúng là việc scale tải request nằm ở phía Backend/DevOps, nhưng ở phía Mobile, scale user đồng nghĩa với scale tính năng và scale team dev. Để đáp ứng, tôi sẽ tập trung vào 3 việc cốt lõi của Kiến trúc App: 
> 1. Chuyển từ cấu trúc thư mục phẳng sang **Feature-based Architecture** hoặc Clean Architecture để team code không dẫm chân nhau. 
> 2. Phân tách rạch ròi **Client State** và **Server State** (như Redux và TanStack Query) để app không bị phình state.
> 3. Tăng cường **Observability**: Gắn Sentry/Crashlytics có kẹp ID của user và session để khi có lỗi ở 10.000 người, mình trace được chính xác luồng lỗi của user đó thay vì mò mẫm trong đống log vô danh."

- **Điểm trung bình:** 4.0 / 5.0
- **Verdict: PASS** (Rất xứng đáng ở level Middle - Strong Middle).

Còn để đo tổng thể kích thước file APK/AAB xem do asset ảnh hay file resource nào nặng, tôi dùng tính năng APK Analyzer có sẵn trong Android Studio."

3. **Voice-to-Text Setup:** Cố gắng phát âm rõ các keyword tiếng Anh hoặc gõ tay các từ khóa chuyên ngành để AI chấm/ghi nhận chính xác hơn (tránh lệch như "FeatureFlash", "Tentacle Query").
